# Архив ИРД на Django

## Django и PostgreSQL

Проект работает только на Django 5.2 и PostgreSQL 16. Ветка `main` обслуживает
приложение на `127.0.0.1:5050`; внешний HTTPS-доступ идёт через ngrok.
Для портала и Django Admin требуется вход. PostgreSQL доступен локально на
`127.0.0.1:5438`. Flask runtime и ветка удалены; общие OCR/документные сервисы
оставлены в `app/` как Django-зависимости. SQLite-резерв и файловый архив
сохранены. Подробности перехода описаны в [`DJANGO_MIGRATION_PLAN.md`](DJANGO_MIGRATION_PLAN.md).

Запуск Django web и PostgreSQL:

```bash
docker compose up --build -d django-web
```

Планировщик OCR и очереди запускается отдельным профилем:

```bash
docker compose --profile post-migration up --build -d django-scheduler
```

При запуске Django применяет миграции и использует постоянный PostgreSQL
volume; старый SQLite-снимок автоматически не импортируется. Финальный импорт
на этой установке выполнен 2026-11-19: из архивной SQLite перенесены 197 строк
в 11 таблиц. После cutover в PostgreSQL появились новые Django-only записи,
поэтому SQLite теперь является архивным снимком, а не источником обновления.
Не запускайте `import_legacy_sqlite --replace` поверх действующей базы.
Резервные копии находятся в `instance/backups/django-cutover-*`; текущие файлы
проекта — в `uploads` и `instance/acts`.

Email-уведомления Django включены; SMTP настроен. Django Admin доступен по
`/admin/`; superuser создаётся отдельно для каждой установки и не входит в
импорт бизнес-данных.

## Возможности

- Проекты с отдельными документами, комплектностью, согласованиями и перепиской.
- Пакетная загрузка PDF и фотографий, включая HEIC; OCR, извлечение реквизитов
  AI-моделью и локальный fallback.
- Редактирование реквизитов, сроков и заметок, архивирование/восстановление
  документов, PDF и Word preview и постраничный просмотр PDF.
- Редактируемые шаблоны комплектности, несколько документов в поддерживаемых
  типах строк, сроки, замена редакций и архивные связи.
- Генерация описей, запросов данных и актов приёма-передачи.
- ZIP-экспорт проекта с JSON-данными, оригиналами и SHA-256 манифестом.
- Регистрация пользователей, вход по email, сброс/смена пароля и личные настройки.
- Панель суперадминистратора для организаций, заказчиков и прав пользователей.
  Уровень «Просмотр» может быть ограничен назначенными заказчиками и отдельными
  объектами; прямые ссылки на документы этих объектов также проверяют доступ.

Новые регистрации получают заблокированный доступ. Суперадминистратор назначает
организацию и уровень доступа в разделе «Управление доступом». Для сброса пароля
должны быть настроены параметры SMTP в `.env`.

```bash
.venv-django/bin/python manage.py check
.venv-django/bin/python manage.py makemigrations --check --dry-run
.venv-django/bin/python manage.py test migration_portal
```

При cutover все 11 таблиц прошли SHA-256 аудит. После cutover Django продолжил
записывать данные в PostgreSQL, поэтому текущее состояние намеренно отличается
от исходной SQLite. Резервные копии PostgreSQL, SQLite и файлов сохранены.

## Подготовка документов для поиска

После OCR исходный `raw_text` сохраняется без переписывания. В той же транзакции
создаётся задача `PreparedDocument`. Планировщик каждые 3 секунды забирает задачи
после распознавания: нормализует текст, согласует метаданные с карточкой, делит
текст по страницам и абзацам и атомарно сохраняет `DocumentChunk`. Только готовые
источники доступны аналитике. При вопросе повторные OCR, нормализация и чанкование
не выполняются. Нормализация и чанкование не вызывают внешнюю AI-модель.

Правка реквизитов обновляет метаданные и сбрасывает кэш ответов, сохраняя чанки.
Правка `raw_text` пересоздаёт чанки. На время обновления источник исключается из
поиска. Статус комплектности читается из актуальных строк проекта при поиске.
Исходный OCR и актуальные реквизиты передаются отдельно: произвольные вхождения
номеров и дат внутри документа не заменяются. Архивные документы и проекты,
а также документы с ошибкой обработки исключены из поиска.

Миграция ставит существующие распознанные источники в очередь. Для немедленной
обработки и проверки результата без повторного OCR:

```bash
docker compose exec django-web python manage.py prepare_documents
# После устранения причины ошибки:
docker compose exec django-web python manage.py prepare_documents --retry-errors
# При изменении правил нормализации или чанкования:
docker compose exec django-web python manage.py prepare_documents --rebuild
```

Правила версионируются константой `PIPELINE_VERSION`. Ошибка подготовки откатывает
новые чанки целиком; сохранённая задача получает статус `error` и текст причины.
Новые PDF с текстовым слоем и OCR сохраняют номера страниц. Для исторического OCR без маркеров страницы восстанавливаются только при точном
совпадении текста с целыми страницами текстового слоя оригинала. Допускается
совпадение с начальными страницами PDF, когда далее идут приложения, не вошедшие
в распознавание письма. Одностраничные PDF однозначно относятся к странице 1.
Если соответствие не подтверждено, номер страницы не назначается. `raw_text`
при восстановлении не меняется; дополнительное OCR не выполняется.

Поиск сохраняет отдельную ссылку на следующую страницу, если найденное требование
продолжается за границей страницы. Для вопросов об историческом письме сохраняется
место для второго фрагмента переписки; актуальное состояние карточки по-прежнему
имеет приоритет в вопросах о текущем статусе.
